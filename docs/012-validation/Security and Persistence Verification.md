# Security and Persistence Verification

## Scope

This verification covers the local simulator/MVP persistence path for SecureVaultKit and the iOS app wiring that uses `VaultEngineFactory.makePersistentLocalEngine(storageURL:)`.

It verifies durability across engine recreation, raw SQLite/blob plaintext inspection, temporary-file cleanup behavior, transaction atomicity, migration safety, file placement, and key/logging guardrails.

## Database Location

The iOS app resolves persistent storage under Application Support through `AppDependencyFactory`.

SecureVaultKit persistent tests use a stable per-test temporary directory with:

```text
<test-storage>/vault.sqlite
<test-storage>/vault.sqlite-wal
<test-storage>/vault.sqlite-shm
```

The production-facing persistent factory does not place the vault database under a temporary directory.

## Blob Location

Persistent local blobs are stored under:

```text
<storageURL>/blobs/{first-two-chars-of-blob-id}/{blob-id}.blob
```

`PersistentLocalBlobStore` mirrors blob records into SQLite and reloads them from SQLite after engine recreation.

## Algorithms and Configuration

Current simulator/MVP persistent configuration uses:

- `FakeCryptoEngine` for vault object metadata/payload encryption.
- `FakeBlobEncryptionEngine` for file/blob transformation.
- `SQLiteStorageEngine` for persistent headers, objects, events, devices, attachment references, and blob records.
- `PersistentLocalBlobStore` for stable file-backed blob bytes plus SQLite-backed blob metadata.

This is sufficient for MVP persistence validation but is not a production crypto claim. Real production blob encryption remains governed by the crypto and blob streaming milestones.

## Plaintext Markers Tested

The test suite persists and scans for:

- `SECURITY_MARKER_PASSPORT_TITLE_7A91`
- `SECURITY_MARKER_NOTE_BODY_8B42`
- `SECURITY_MARKER_DOCUMENT_NUMBER_9C53`
- `SECURITY_MARKER_CARD_NUMBER_0D64`
- `SECURITY_MARKER_BLOB_CONTENT_E175`

## Raw Database Inspection Method

Tests read raw bytes from:

- `vault.sqlite`
- `vault.sqlite-wal`, when present
- `vault.sqlite-shm`, when present

The marker byte sequences were not found in the SQLite database or sidecar files.

## Blob Inspection Result

Tests enumerate all persisted `.blob` files under the persistent blob directory and scan raw bytes for `SECURITY_MARKER_BLOB_CONTENT_E175`.

The marker was not found in original, thumbnail, or preview blob files generated by the fake encrypted blob pipeline.

## Temporary-File Cleanup Result

Existing and added tests verify:

- Document import removes its temporary workspace after success.
- Blob encryption failure removes partial output.
- Cancellation paths remove written blobs where IDs are known.
- Storage failure after blob write removes valid partial blob records from the blob store.

Remaining limitation: cancellation or failure after object insertion is transaction-safe on the SQLite import path, but in-memory test fakes are still best-effort rollback helpers rather than a production transaction system.

## Transaction Atomicity Result

Verified:

- SQLite object + attachment + event persistence runs inside one transaction.
- Duplicate attachment failure rolls back object insertion and event append.
- Persistent document import now stores object, attachment references, and import events through SQLite transaction support.
- Blob write followed by object creation failure deletes written blobs and does not expose a visible object or success event.

## Migration Result

Verified:

- Migration version `v1` is tracked in `schema_migrations`.
- Migration execution is idempotent.
- Unsupported future schema versions fail explicitly with `SQLiteStorageError.unsupportedSchemaVersion`.
- Corrupted databases fail safely and preserve the original file.
- Migration failure does not partially mark `v1` as applied.
- Missing required tables fail rather than silently recreating an empty vault over existing data.

## File Protection Status

The persistent iOS path uses Application Support for app-owned data. SQLite and blob file protection/backup exclusion are documented as required for production hardening, but platform-specific file protection is not fully wired in SecureVaultKit yet.

Known simulator limitation: iOS file protection behavior is not reliably validated through macOS SwiftPM tests. A follow-up should add an Apple-platform infrastructure helper for:

- database file protection attributes
- blob directory protection attributes
- backup exclusion policy

## Key Persistence Verification

Current verification confirms:

- Raw `SymmetricKeyMaterial` is runtime-only in model design and is not persisted directly by SQLite tests.
- Recovery package tests ensure recovery secret is not exported.
- Existing secure key store tests assert SecureKeyStore source does not use `UserDefaults`, `print`, `debugPrint`, `Logger`, or `os_log`.
- Keychain remains the intended Apple-platform storage boundary for locally protected key material where wired.

## Logging Audit

Searches were performed for:

- `print(`
- `debugPrint(`
- `NSLog(`
- `Logger`
- `os_log`

No production logging of vault titles, note bodies, identity numbers, card numbers, recovery secrets, file contents, raw paths, key material, or unnecessary ciphertext was found. Matches in tests are guardrail assertions.

## Known Limitations

- Persistent local MVP still uses fake crypto and fake blob transformation.
- File protection and backup exclusion need a dedicated Apple-platform hardening helper.
- `FileSystemBlobStore.writeBlob(_ data:)` remains a compatibility path for small fake writes and may stage data in memory; document import uses file-based encrypted blob output.
- Automatic corrupted database recovery is intentionally not implemented.
